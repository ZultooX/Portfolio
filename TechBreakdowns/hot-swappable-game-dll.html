Hot-Swappable Game DLL
How I made it possible to change game code and recompile it without restarting Eclipsed Engine's editor.

Why a DLL?

In Eclipsed Engine the game is not part of the editor. The editor is one program, and all of the game code is compiled into its own dynamic library that the editor loads when it starts.

The reason is simple. Code that is compiled into the editor can't be changed while the editor is running. A library can be unloaded and loaded again, so the editor can throw away the old game code and load the new without restarting.

Loading the game

The editor doesn't know anything about the game it loads. It doesn't know which components exist or what they are called. The only thing it knows is the name of one function that every game library has: RegisterReflectedTypes. 
bool GameModuleManager::Load()
{
    gameModule = LoadLibraryA(dllPath.generic_string().c_str());
    if (!gameModule)
        return false;

    registerReflectedTypesFunc = (Func)GetProcAddress((HMODULE)gameModule, "RegisterReflectedTypes");
    if (!registerReflectedTypesFunc)
        return false;

    registerReflectedTypesFunc();

    return true;
}
That function is not written by hand. It is generated by my reflection system, and it registers every component in the game. After it has been called, the editor can create the game's components, show them in the inspector and save them, without ever including a single game header.

Recompiling

When you press Recompile in the editor, this is what runs: 
bool GameModuleManager::Reload()
{
    SceneManager::UnloadActive();
    const bool ok = TryCompileAndLoad();

    SceneManager::ReloadActive();

    return ok;
}
The order is important. The scene has to be unloaded first, because every game component in it is running code that lives inside the library. If the library was unloaded while the components were still alive, they would point at code that no longer exists and the editor would crash.

With the scene gone it is safe to swap the library: 
bool GameModuleManager::BuildDLL()
{
    if (IsLoaded())
        Unload();

    bool wasChanged = HasChanged();

    if (wasChanged && !RunHeaderTool())
        return false;

    if (wasChanged && !GenerateCmake())
        return false;

    if (wasChanged && !Compile())
        return false;

    if (!CopyDllFile())
        return false;

    return true;
}
  1. Unload: the old library is freed.
  2. HeaderTool: the game's headers are scanned and the reflection code is generated again, so new components and fields are picked up.
  3. CMake: the project is generated again, so new files are included.
  4. Compile: the game is built into a new library.
  5. Copy: the new library is copied next to the editor.

After that the new library is loaded, its types are registered and the scene is loaded again.

The copy in the last step is there for a reason. Windows locks a library for as long as it is loaded. The editor loads the copy, which leaves the original free to be overwritten by the compiler.

Only when needed

Compiling takes time, and most of the time when the editor starts nothing has changed. So before building, the editor compares the last write time of the library with every file in the project's Content folder. If no file is newer than the library, the three build steps are skipped and the existing library is loaded directly. 
for (auto& entry : fs::recursive_directory_iterator(PathManager::GetProjectRoot() / "Content"))
{
    if (!entry.is_regular_file())
        continue;

    if (fs::last_write_time(entry.path()) > dllLastWriteTime)
        return true;
}

return false;

When the build fails

Game code is going to have compile errors, and the editor has to survive that. Each build step runs as its own process and writes its output to a log file. If a step fails, the editor shows an error in the console with the path to the log, and remembers that the game has build errors.

While there are build errors the editor keeps running, but without a game library. So it blocks the things that would go wrong without one: you can't enter play mode, and you can't save the scene. When the code is fixed and recompiled, everything is unlocked again.

What it can't do

The system is not perfect, and there are things I know it can't handle:
  • It is a reload, not a live patch. The scene is loaded again from its saved state, so changes that were not saved are lost when recompiling.
  • The editor waits. The build runs while the editor is blocked, so you can't keep working while the game compiles.
  • It only works on Windows. Loading the library is done directly with the Windows API.
