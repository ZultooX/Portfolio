C++ Runtime Reflection
Inspect and manipulate values directly from Eclipsed Engines Unity-like editor.

What is reflection?

Reflection can mean different things, from the reflection you see in the mirror to being able to reflect and inspect values of types.

Using reflection we are able to inspect and set values to different types without being able to access the type itself.

Where it all started

When starting development of Eclipsed Engine we knew that a future issue that we where going to face where how we would manipulate positions and other values from the editor.

The first system I developed were that all values that we would access from the editor had to be its own templated type. I called it SERIALIZED_FIELD which I wrapped in macros to make it easier to use, but since I stored all of the meta data of the type and the variable in the type itself meant that all instances of the class gained the same values. This meant that every class grew exponentially, the engines SpriteRenderer2D class grew to about 912 bytes per instance. 
class ObstacleSpawner : public Eclipse::Component
{
    COMPONENT_BASE_2(ObstacleSpawner, 3)
public:
    void Start() override;
    void Update() override;
private:
    SERIALIZED_FIELD(Eclipse::Assets::Prefab, ObstaclePrefab);
    SERIALIZED_FIELD(float, ObstacleSpawnInterval, 2);
    float obstacleSpawnTimer = 0.f;
};
We decided that this was a future issue, it worked and made it easy to continue and focus on other areas of the engine. But as our needs grew, so did the class sizes.

Back to the drawing board

The first system taught me what I needed to get right:
  • Metadata belongs to the type, not the instance. A field's name and type are the same for every instance, so they should be stored once.
  • No macros. A reflected field should look like any other member variable.
  • It has to be extensible. We wanted to mark fields for more than the editor.

So I moved reflection out of the classes and into the build. Fields are marked with an attribute such as [[serializefield]], and before compiling, a tool scans every source file and generates the metadata for each marked class. That metadata exists once per type, no matter how many instances there are.

The generated file stored the field names, type names, field size and field offsets to the type. 
class ObstacleSpawner : public Eclipse::Component
{
    MAKE_REFLECTABLE(ObstacleSpawner);
    REFLECTION_FLAG(COMPONENT);

    COMPONENT_BASE_2(ObstacleSpawner, 3)
public:
    void Start() override;
    void Update() override;
private:
    [[SerializedField]]
    Eclipse::Assets::Prefab ObstaclePrefab;

    [[SerializedField]]
    float ObstacleSpawnInterval = 2;

    float obstacleSpawnTimer = 0.f;
};

How it works

A HeaderTool scans all of the header files at a location, and collects data on of the type using regex. Then with the information it collected it then generates a header file and fills it with the types, the attributes and all of the fields.

This happens once.

Eclipsed Engine reflects the Engine project when you rebuild the cmake project. And reflects the game project when rebuilding the dynamic library.
This is the code that is generated per type. 
template<> struct ReflectionRegistrar<ObstacleSpawner>
{
	static inline void Register()
	{
		Reflection::ReflectionRegistry::RegisterType(
			TypeEntry{
				.name = "ObstacleSpawner", 
				.size = sizeof(ObstacleSpawner),
				.id = Type::GetTypeID<ObstacleSpawner>(),
				.create = [](){ return reinterpret_cast<void*>(new ObstacleSpawner); },
				.createAtAddress = [](unsigned char* addr){ return reinterpret_cast<void*>(new (addr)ObstacleSpawner); },
				.destroy = [](void* data){ delete reinterpret_cast<ObstacleSpawner*>(data); },
				.flag = static_cast<Reflection::ReflectionFlags>(1),
				.fieldOrder = { "ObstaclePrefab", "ObstacleSpawnInterval" }
			}
		);

		{
			FieldEntry entry =
			{
				.name = "ObstacleSpawnInterval",
				.owner = "ObstacleSpawner",
				.offset = offsetof(ObstacleSpawner, ObstacleSpawnInterval),
				.size = sizeof(ObstacleSpawner::ObstacleSpawnInterval),
				.type = Type::GetTypeID<decltype(ObstacleSpawner::ObstacleSpawnInterval)>()
			};

			Reflection::ReflectionRegistry::RegisterType<decltype(ObstacleSpawner::ObstacleSpawnInterval)>();
			entry.attributeContainer.Add<SerializeField>();

			Reflection::ReflectionRegistry::RegisterField(
				"ObstacleSpawner",
				entry
			);
		}

		{
			FieldEntry entry =
			{
				.name = "ObstaclePrefab",
				.owner = "ObstacleSpawner",
				.offset = offsetof(ObstacleSpawner, ObstaclePrefab),
				.size = sizeof(ObstacleSpawner::ObstaclePrefab),
				.type = Type::GetTypeID<decltype(ObstacleSpawner::ObstaclePrefab)>()
			};

			Reflection::ReflectionRegistry::RegisterType<decltype(ObstacleSpawner::ObstaclePrefab)>();
			entry.attributeContainer.Add<SerializeField>();

			Reflection::ReflectionRegistry::RegisterField(
				"ObstacleSpawner",
				entry
			);
		}
	}
};

The tool then generates one more file that calls every reflected type's Register method. It does this from the constructor of a static object.

Why? A static object is constructed automatically when the program starts, before main() runs. Nobody has to call an init function or remember to add a new component to a list. If a component is reflected, it is registered. 
struct ComponentsStaticInitiator
{
	ComponentsStaticInitiator()
	{
		ReflectionRegistrar<Canvas>::Register();
		ReflectionRegistrar<SpotLight2D>::Register();
		ReflectionRegistrar<AudioEmitter>::Register();
		ReflectionRegistrar<Camera>::Register();
		ReflectionRegistrar<RigidBody2D>::Register();
		ReflectionRegistrar<AmbientLight2D>::Register();
		ReflectionRegistrar<DirectionalLight2D>::Register();
		ReflectionRegistrar<PointLight2D>::Register();
		ReflectionRegistrar<ParticleSystem2D>::Register();
		ReflectionRegistrar<Transform2D>::Register();
		ReflectionRegistrar<SpriteRenderer2D>::Register();

	}
};

inline ComponentsStaticInitiator __componentsStaticInititator = {};

The results

With the new system, I was able to move all of the type data to a central location, and not tied to a class instance. And we could simply add an attribute to the variable to add a slider, or add a method it calls when changed.

But most importantly the reflected values are not accessed through a container type, it can be accessed directly.

The class sizes also shrunk as a result of the centralized storage. SpriteRenderer2D shrunk down to 272 bytes.
