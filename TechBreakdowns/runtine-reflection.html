C++ Runtime Reflection
How I built the system that lets us inspect and edit values directly from Eclipsed Engine's Unity-like editor.

What is reflection?

Reflection can mean different things, from the reflection you see in the mirror to a program being able to inspect its own types.

Using reflection we are able to read and set the fields of a type without knowing what the type is. The C++ we use doesn't have this built in, so we had to build it ourselves.

Where it all started

When starting development of Eclipsed Engine we knew that a future issue we were going to face was how we would edit positions and other values from the editor.

In the first system I developed, every value that we wanted to access from the editor had to be wrapped in its own templated type. To make that easier to use I hid it behind a macro called SERIALIZED_FIELD. 
class ObstacleSpawner : public Eclipse::Component
{
    COMPONENT_BASE_2(ObstacleSpawner, 3)
public:
    void Start() override;
    void Update() override;
private:
    SERIALIZED_FIELD(Eclipse::Assets::Prefab, ObstaclePrefab);
    SERIALIZED_FIELD(float, ObstacleSpawnInterval, 2);
    float obstacleSpawnTimer = 0.f;
};
The problem was that I stored all of the metadata of the type and the variable in the field itself. That meant every instance of a class carried its own copy of the same data, and the class sizes ballooned. The engine's SpriteRenderer2D class grew to about 912 bytes per instance.

We decided that this was a problem for later. It worked, and it made it easy to continue and focus on other areas of the engine. But as our needs grew, so did the class sizes.

Back to the drawing board

The first system taught me what I needed to get right:
  • Metadata belongs to the type, not the instance. A field's name and type are the same for every instance, so they should be stored once.
  • No wrapper types. A reflected field should be a normal member variable, not something hidden behind the SERIALIZED_FIELD macro.
  • It has to be extensible. We wanted to mark fields for more than just showing them in the editor.

So I moved reflection out of the classes and into the build. Fields are marked with an attribute such as [[SerializeField]], and before compiling, a tool scans the header files and generates the metadata for each marked class. That metadata exists once per type, no matter how many instances there are.

The same component now looks like this: 
class ObstacleSpawner : public Eclipse::Component
{
    MAKE_REFLECTABLE(ObstacleSpawner);
    REFLECTION_FLAG(COMPONENT);

    COMPONENT_BASE_2(ObstacleSpawner, 3)
public:
    void Start() override;
    void Update() override;
private:
    [[SerializeField]]
    Eclipse::Assets::Prefab ObstaclePrefab;

    [[SerializeField]]
    float ObstacleSpawnInterval = 2;

    float obstacleSpawnTimer = 0.f;
};
I couldn't get around all of the macros, the class still needs a few to set itself up. But the fields are plain variables again, and the reflected data is not bound to the SERIALIZED_FIELD macro anymore.

How it works

A tool I call HeaderTool scans all of the header files in a project and collects data on the types using regex. With that information it generates a header file for every reflected type and fills it with the type, its attributes and all of its fields.

For each field it stores the name, the type, the size and the offset into the class. That is everything the editor needs to find a field in any instance and read or write it.

This happens when building, not while the game is running. Eclipsed Engine reflects the engine project when you rebuild the CMake project, and the game project when you rebuild the dynamic library.

This is the code that is generated for ObstacleSpawner: 
template<> struct ReflectionRegistrar<ObstacleSpawner>
{
    static inline void Register()
    {
        Reflection::ReflectionRegistry::RegisterType(
            TypeEntry{
                .name = "ObstacleSpawner",
                .size = sizeof(ObstacleSpawner),
                .id = Type::GetTypeID<ObstacleSpawner>(),
                .create = [](){ return reinterpret_cast<void*>(new ObstacleSpawner); },
                .createAtAddress = [](unsigned char* addr){ return reinterpret_cast<void*>(new (addr)ObstacleSpawner); },
                .destroy = [](void* data){ delete reinterpret_cast<ObstacleSpawner*>(data); },
                .flag = static_cast<Reflection::ReflectionFlags>(1),
                .fieldOrder = { "ObstaclePrefab", "ObstacleSpawnInterval" }
            }
        );

        {
            FieldEntry entry =
            {
                .name = "ObstacleSpawnInterval",
                .owner = "ObstacleSpawner",
                .offset = offsetof(ObstacleSpawner, ObstacleSpawnInterval),
                .size = sizeof(ObstacleSpawner::ObstacleSpawnInterval),
                .type = Type::GetTypeID<decltype(ObstacleSpawner::ObstacleSpawnInterval)>()
            };

            Reflection::ReflectionRegistry::RegisterType<decltype(ObstacleSpawner::ObstacleSpawnInterval)>();
            entry.attributeContainer.Add<SerializeField>();

            Reflection::ReflectionRegistry::RegisterField(
                "ObstacleSpawner",
                entry
            );
        }

        // ...and one block like this for every other reflected field
    }
};
The tool then generates one more file that calls every reflected type's Register method. It does this from the constructor of a static object.

Why? A static object is constructed automatically when the program starts, before main() runs. Nobody has to call an init function or remember to add a new component to a list. If a component is reflected, it is registered. 
struct ComponentsStaticInitiator
{
    ComponentsStaticInitiator()
    {
        ReflectionRegistrar<Canvas>::Register();
        ReflectionRegistrar<SpotLight2D>::Register();
        ReflectionRegistrar<AudioEmitter>::Register();
        ReflectionRegistrar<Camera>::Register();
        ReflectionRegistrar<RigidBody2D>::Register();
        ReflectionRegistrar<AmbientLight2D>::Register();
        ReflectionRegistrar<DirectionalLight2D>::Register();
        ReflectionRegistrar<PointLight2D>::Register();
        ReflectionRegistrar<ParticleSystem2D>::Register();
        ReflectionRegistrar<Transform2D>::Register();
        ReflectionRegistrar<SpriteRenderer2D>::Register();
    }
};

inline ComponentsStaticInitiator __componentsStaticInititator = {};

With every type registered, reading and writing a field is simple. The engine looks up the field and uses its offset to find the value inside the object. If the field has an OnChange attribute, its method is called after the value is set. 
void Set(const std::string& typeName, const std::string& fieldName, void* obj, const void* data)
{
    const FieldEntry& field = ReflectionRegistry::GetField(typeName, fieldName);
    ::memcpy(reinterpret_cast<char*>(obj) + field.offset, data, field.size);

    const OnChange* onChange = field.attributeContainer.TryGet<OnChange>();
    if (onChange)
    {
        onChange->event(obj);
    }
}

void* Get(const std::string& typeName, const std::string& fieldName, void* obj)
{
    const FieldEntry& field = ReflectionRegistry::GetField(typeName, fieldName);
    return reinterpret_cast<char*>(obj) + field.offset;
}
This is what the editor uses to show and change values, without knowing anything about the class it is editing.

The results

SpriteRenderer2D went from about 912 bytes per instance down to 272, around 70% smaller. All of the type data now lives in one central place and is no longer tied to a class instance.

The reflected values are also not accessed through a wrapper type anymore. They are normal variables that can be used directly.

And adding more is simple. We can add an attribute to a variable to give it a slider, or to call a method when it is changed, like [[SerializeField, OnChange(OnChangeSprite)]].
