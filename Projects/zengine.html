Zengine
Zengine is my own C++ game engine built on DirectX 11. It began in the Applied Graphics Programming course at The Game Assembly, and I kept developing it on my own afterwards. Everything listed here is work I did on my own, outside the course.

At a glance

  • Team: Solo
  • Tech: C++, DirectX 11, ImGui
  • What I built: an ImGui editor, an ECS, shader compilation with reflection, asset management, and the inverse kinematics for my FABRIK specialization

ImGui editor

During the course I wanted to test values like lighting and camera settings without rebuilding the engine every time. So I integrated ImGui and added sliders, buttons and input fields for adjusting things like light intensity and camera position while the engine was running. Seeing changes instantly, without stopping or recompiling, made testing much faster and cut down a lot of waiting.

ECS

After a presentation about entity component systems I wanted to learn how they work. I store components in pools so components of the same type sit next to each other in memory, which lowers the chance of cache misses. Logic lives in systems, which share an ISystem interface so they can be stored together.

Building it taught me a lot about working with entities instead of game objects. In the end I prefer component systems where the logic lives inside the components. In my implementation the logic for several components often ended up in the same system, which made the code harder to follow.

Shader compiling

I wanted an easier way to give shaders textures and variables without writing a custom buffer for each one. DirectX 11 has shader reflection, which lets you read every texture and buffer bound to a shader program.

One catch is that variables have to be inside a constant buffer to be reflected. So the engine looks for a buffer named PublicContainer in each shader and reads the variables from it.

To avoid reflecting the shader every time it loads, the reflected textures, variables and buffers are saved to a material file. On later loads the engine just reads the material file and reapplies the values, which saves redundant work and makes shader management more flexible.
